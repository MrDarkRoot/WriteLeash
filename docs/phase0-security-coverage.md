## Priority outcomes and follow-ups

1. **Observed F (policy interference):** `R` reproduces the shared-counter denial with fresh durable-state checks and a sticky poison at precommit. It is *overrestriction* (no unauthorized durable effect observed), but prevents any claim of correctly independent per-table budgets. Owner: #9/#11 maintainer; define independently keyed policy/effect metrics and rerun cross-table both directions after approved numeric semantics; do not edit the accepted spec to fit the counter.
2. **Uncharacterized reachable paths:** deeper/mixed exception subtransaction graphs and writer-reachable callable paths should be tested before widening the narrow envelope. Stored `SECURITY DEFINER` functions, FKs and partitions cannot be described as safely excluded in an arbitrary installation merely because this fixture has none. Any *supported* effect that escapes and commits is a security failure: stop for review and propose permanent `CC-REG-YYYY-NNN` test (none yet proven here).
3. **Benchmark:** plan a disposable PG16.4 baseline without the trigger vs protected version with identical synthetic rows, plan, role and warmup; measure p50/p95/p99 latency, transactions/sec and rows/sec for 1/5/100-row updates (100-row budget requires trusted test config). No comparable baseline harness/results exist; **NOT MEASURED**.

## Transaction-splitting conflict — DECISION REQUIRED from founder

ADR-005 explicitly defers capability-wide budgets, but founder Success Checklist #1 (quoted in [issue #11](https://github.com/MrDarkRoot/CommitCap/issues/11)) says budget excess cannot commit “even transaction splitting.” Concrete experiment: writer TX1 updates rows 1–5 and COMMITs, writer TX2 updates rows 6–10 and COMMITs; a fresh admin reads ten changed rows, each individual transaction consumed only 5/5. R's same-backend legacy CC-021 autocommit reuse already does precisely two committed five-event transactions and verifies the exact ten-row state (`R:1704–1716`, E8/E11). This **satisfies the current transaction-local rule**, but **does not** satisfy task-wide budget 5 or the checklist's stronger wording.

- **Route A — narrower Phase 0 proof:** founder explicitly changes Success Checklist #1 wording to: “Within one top-level transaction, no supported durable relational effect exceeds its independently declared per-transaction authority; work split across transactions is outside this proof and does not establish task-wide safety.” Keep ADR-005 strategic future gate. Even then numeric #9, bypass coverage, performance and #10 deployment constraints remain open. Do **not** call this a pass of the original stronger checklist.
- **Route B — stronger checklist gate:** retain “even transaction splitting,” and require a **separate future scoped issue** for capability-wide durable atomic consumption across transactions/concurrent writers, retries, idempotency keys/ambiguous commit, crash recovery and monotonic authority (inverse writes cannot launder budget). Prove canonical CC-034/035, 070/071, 080–082 and 090 with fresh durable oracle before declaring Success Checklist #1 passed. No implementation proposed in this PR.

Neither route is selected here. No ADR/checklist is silently rewritten. Phase 0 Technical Proof #1 is **not checked off**; #9 numeric, independent policy accounting, high-risk alternate paths, and baseline performance remain gates. #10 separately constrains real managed deployment; local research evidence proves neither deployment nor the task-wide statement.
