# Numeric-delta Phase 0 semantic decision (issue #9)

Status: **PROPOSED — MAINTAINER DECISION REQUIRED; implementation blocked**. Reviewed 2026-09-23 against `origin/main` at `2538963906967f2a7d7ae79e6dfdc992a3b7d199`.

This is a narrow PostgreSQL 16.4 research proposal for `refunds.amount.total_positive_delta <= 100` **per top-level transaction**. It measures a declared relational effect, not external payments. It does not grant cross-transaction authority (`CC-034/035`). See [spec §§2–4, 14](spec.md), [canonical test plan §8](test-plan.md), ADR-003/004/005/012/017/018 in [decisions](decisions.md).

## Semantic decision table

| Question | Already specified | Proposed interpretation for review / test sketch |
| --- | --- | --- |
| OLD → NEW | `delta = NEW.amount - OLD.amount` (spec §3); `total_positive_delta` used in CC-030–033. | For each *supported UPDATE row effect*, add `max(delta, 0)` to this metric; never derive it by comparing final row values. A +80 then -80 consumes 80 (CC-033). **Approve event granularity and UPDATE-only fixture.** |
| Several statements, same row | Transaction-wide accumulation mandatory (ADR-004); row-count experiment counts every update event, including same-row/no-op. Numeric repeated-row behavior not explicitly fixed. | 0→40→80 consumes 80; 0→80→0→30 attempts 110 and must poison the transaction. One bulk UPDATE + several small UPDATEs must share the metric. **Approve independently of row-event count semantics.** |
| Zero and negative change | Spec §5 says `total_positive_delta` ignores negative deltas; CC-033 explicitly forbids netting +80/-80. | Equal OLD/NEW and negative-only update consume 0 *numeric* authority, but still one row-update event if a row policy is attached. A later positive update must not regain spent positive authority. |
| Allowed rollback | Spec §4.3 *prefers* restoration of rolled-back transaction-local work, not an unconditional settled rule; existing native row experiment unwinds allowed subtransaction deltas. | Roll back +80 inside a savepoint, then +100 and commit: 100 effective; nested release-to-parent then outer rollback also unwinds. **Confirm preferred semantic.** |
| Denial inside savepoint/exception | Spec §4.2 requires abort; existing native `denied` flag survives subtransaction abort and PRE_COMMIT rejects. | Attempt +101 under a savepoint or catch the error: later SQL may execute, but COMMIT must error and *all* sibling writes must roll back. Denial must never be unwound by restoring allowed consumption. |
| Column and unit | Spec/test-plan use `amount` and examples 30/20/40/100, **do not specify SQL type, precision, NULL policy, currency, or rounding**. | Test-only unconstrained `numeric` with explicit checks for finite, nonnegative, at most 16 integer digits and at most two fractional digits; budget exactly `100.00` in the same unit. Reject over-scale input before storage rather than use `numeric(18,2)` (whose input coercion rounds *before* a row trigger/check can inspect it). No float conversion. **All these choices require approval.** |
| Special values / NULL | No numeric NULL/NaN/Infinity semantics in spec §3. | Reject NULL, NaN, and both infinities *before* effect measurement, including any alternative assignment or fixture setup path; prove writer cannot relax constraints. If approval favors another rule, change proposal/tests before implementation. |
| Budget bounds / overflow | Numeric budget range/representation undefined; historical native *row* `int32` GUC and `uint64` counter are not numeric-delta semantics. | Nonnegative finite fixed-scale budget, compare exactly and check sum before adding. Reject unrepresentable budget/input/accumulation with sticky denial rather than wrap/clamp; test 0, 100.00, 100.01, extreme precision/magnitude. Define maximum and validation channel with maintainer before code. |
| Isolation and concurrent sessions | Spec §6 atomicity is for **capability-wide**, not independent transaction-local budgets. Row experiment tested two backends under READ COMMITTED only. | Each backend has its own transaction-local amount; concurrent writers contending for one refund row should measure the actual locked OLD→NEW effect exactly once. Test READ COMMITTED; other isolation levels remain untested until separately scoped. |
| Independent policies and effect classes | Spec §3: row counts *per protected table*; §8 illustrates distinct table/transition/effect rules. | `subscriptions` row budget 5, `users` allowed transitions and `refunds` amount 100 must not share or reset another policy's consumption; one refunds UPDATE may consume both its own row-event budget (if declared) and numeric amount exactly once. A violation of either poisons the same top-level transaction. **Existing native `ExperimentState.consumed` is a single shared counter for subscriptions and users; no per-table metric exists. This is a composition blocker, not evidence of independent policy budgets.** |

## Reviewable adversarial tests (not yet implemented)

Use owner `commitcap_owner`/writer `commitcap_writer`, a new minimal `refunds(id, customer_id, amount)` fixture, test-only protected C trigger, restricted column grants, and a fresh trusted-admin connection for **every** durable assertion. Run canonical `CC-030`: +30/+20/+40 → 90 commit; `CC-031`: exactly 100 commit; `CC-032`: single +101 and decomposed 30+20+40+11 → denial and whole-transaction abort; `CC-033`: +80/-80 then +21 → deny (not net zero), and +80/-80 only → commit with positive consumption 80. Assert both command outcome and exact rows after commit/abort; never substitute historical same-number row-budget results.

Boundary probes: repeated updates of one row; zero-row and no-op UPDATEs; negative-only delta; fractions 0.01, 100.00, 100.01 and excess scale; NULL/NaN/±Infinity; extreme numeric and aggregate overflow. Savepoint: rollback allowed +80 then commit +100; nested savepoint release followed by outer rollback; attempted +101 inside savepoint then ROLLBACK TO and attempted ordinary UPDATE + sibling audit INSERT before rejected COMMIT; PL/pgSQL handler catches over-budget error then COMMIT still fails. Confirm new transaction/backend cleanup, constrained grants, CTE/prepared/`EXPLAIN ANALYZE` update entry points, and multi-table composition: five subscription updates plus allowed user transition (the current shared counter would deny the sixth), then a refund +100; negative tests independently exceed each defined policy.

The current [native C state](../experiments/native_tx_state/commitcap_native_tx_state.c) only has `uint64 consumed`, `budget` and per-subtransaction row-count `delta` shared by both triggers. `setup.sql` has no refunds fixture; extension SQL has no numeric function; `run.sh`'s legacy `CC-030`–`CC-033` are *row* tests. None of the canonical numeric cases have run. **Do not implement enforcement or claim PASS until the maintainer approves exact type, input/rounding/NULL/special-value/bounds semantics and policy independence.** The smallest candidate after approval is separately keyed transaction-local counters and rollback frames plus one fixed-rule C trigger sharing the existing sticky-denial bit; if that cannot maintain denial, retain the failure reproduction instead of redesigning here.
