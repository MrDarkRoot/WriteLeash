# Numeric-delta Phase 0 semantic decision (issue #9)

Status: **APPROVED FOR POSTGRESQL 16.4 RESEARCH FIXTURE ONLY** by the [PR #12 maintainer review](https://github.com/MrDarkRoot/CommitCap/pull/12#issuecomment-5792009512) and [issue #9 decision](https://github.com/MrDarkRoot/CommitCap/issues/9#issuecomment-5792038528). Original review base: `origin/main` `2538963906967f2a7d7ae79e6dfdc992a3b7d199`. Not a production policy/unit/precision contract.

This is a narrow PostgreSQL 16.4 research proposal for `refunds.amount.total_positive_delta <= 100` **per top-level transaction**. It measures a declared relational effect, not external payments. It does not grant cross-transaction authority (`CC-034/035`). See [spec §§2–4, 14](spec.md), [canonical test plan §8](test-plan.md), ADR-003/004/005/012/017/018 in [decisions](decisions.md).

## Semantic decision table

| Question | Canonical source | Approved experiment decision |
| --- | --- | --- |
| OLD → NEW | `delta = NEW.amount - OLD.amount` (spec §3); `total_positive_delta` used in CC-030–033. | Each supported refunds UPDATE row effect adds `max(delta, 0)` in exact PostgreSQL numeric arithmetic, not the difference between final row values. +80 then -80 consumes 80 (CC-033). |
| Several statements, same row | Transaction-wide accumulation mandatory (ADR-004); row-count experiment counts every update event, including same-row/no-op. | 0→40→80 consumes 80; 0→80→0→30 attempts 110 and poisons the transaction. Bulk and decomposed UPDATEs share the numeric metric, independent of row counts. |
| Zero and negative change | Spec §5 says `total_positive_delta` ignores negative deltas; CC-033 explicitly forbids netting +80/-80. | Equal OLD/NEW and negative-only update consume 0 *numeric* authority, but still one row-update event if a row policy is attached. A later positive update must not regain spent positive authority. |
| Allowed rollback | Spec §4.3 prefers restoration; native row experiment unwinds allowed subtransaction deltas. | Roll back +80 inside a savepoint, then +100 and commit: 100 effective; nested release-to-parent then outer rollback also unwinds. Only allowed provisional consumption is restored. |
| Denial inside savepoint/exception | Spec §4.2 requires abort; existing native `denied` flag survives subtransaction abort and PRE_COMMIT rejects. | Attempt +101 under a savepoint or catch the error: later SQL may execute, but COMMIT must error and *all* sibling writes must roll back. Denial must never be unwound by restoring allowed consumption. |
| Column and unit | Canonical examples do not define SQL type, precision, NULL or rounding; maintainer review fixes test-only semantics. | Unconstrained `numeric`, finite nonnegative amounts with <=16 integer digits and <=2 fractional digits, no floating-point or `numeric(p,s)` input rounding. Check both OLD and NEW before subtraction/accounting. Numeric budget defaults to 100.00. These fixture limits are not a monetary claim. |
| Special values / NULL | No numeric special-value semantics in spec §3; maintainer review sets fixture limits. | Deny NULL, NaN, +Infinity, -Infinity and invalid OLD or NEW before effect accounting. Writer has UPDATE(amount) only, no INSERT/DDL/constraint changes. |
| Budget bounds / overflow | Historical native *row* int32 GUC/uint64 counter are not numeric-delta semantics. | Test-only superuser-settable exact decimal budget `0.00..9999999999999999.99`, two fractional digits; reject negative, exponent/invalid format, NaN/infinities, excess digits/scale. Compare positive delta with remaining authority **before** adding; exact numeric accumulation cannot wrap/round. Test maximum boundary and writer SET/RESET denial. |
| Isolation and concurrent sessions | Spec §6 atomicity is for **capability-wide**, not independent transaction-local budgets. Row experiment tested two backends under READ COMMITTED only. | Each backend has its own transaction-local amount; concurrent writers contending for one refund row should measure the actual locked OLD→NEW effect exactly once. Test READ COMMITTED; other isolation levels remain untested until separately scoped. |
| Independent policies and effect classes | Spec §3: row counts *per protected table*; §8 illustrates distinct rules. | Separate subscriptions and users row-event counters (each test-only limit five) and a distinct refunds positive-delta metric (test-only limit 100.00). An allowed users transition consumes one **users** row event, not subscriptions or refunds authority. One shared sticky denied bit poisons COMMIT for any policy violation. The former single `ExperimentState.consumed` was overrestrictive; fixing it here precedes numeric enforcement. |

## Adversarial test plan (approved scope)

Use owner `writeleash_owner`/writer `writeleash_writer`, a new minimal `refunds(id, customer_id, amount)` fixture, test-only protected C trigger, restricted column grants, and a fresh trusted-admin connection for **every** durable assertion. Run canonical `CC-030`: +30/+20/+40 → 90 commit; `CC-031`: exactly 100 commit; `CC-032`: single +101 and decomposed 30+20+40+11 → denial and whole-transaction abort; `CC-033`: +80/-80 then +21 → deny (not net zero), and +80/-80 only → commit with positive consumption 80. Assert both command outcome and exact rows after commit/abort; never substitute historical same-number row-budget results.

Boundary probes: repeated updates of one row; zero-row and no-op UPDATEs; negative-only delta; fractions 0.01, 100.00, 100.01 and excess scale; NULL/NaN/±Infinity; 16-digit integer maximum and magnitude/aggregate overflow. Savepoint: rollback allowed +80 then commit +100; nested savepoint release followed by outer rollback; attempted +101 inside savepoint then ROLLBACK TO and attempted ordinary UPDATE + sibling audit INSERT before rejected COMMIT; PL/pgSQL handler catches over-budget error then COMMIT still fails. Confirm new transaction/backend cleanup, constrained grants, CTE/prepared/`EXPLAIN ANALYZE` update entry points, and multi-table composition in **both orders**: five subscription updates plus allowed user transition plus permitted refund; negative tests independently exceed each defined policy. Every PASS checks fresh trusted-admin durable rows.

Pre-implementation baseline: [native C state](../experiments/native_tx_state/writeleash_native_tx_state.c) has a shared `uint64 consumed`; `run.sh`'s legacy `CC-030`–`CC-033` are *row* tests and are not numeric evidence. The approved smallest candidate uses fixed, separately keyed transaction-local counters/rollback frames and one fixed-rule numeric trigger, sharing only sticky denial. If the invariant cannot be maintained, preserve a deterministic failure instead of broadening architecture here.
