# E — Reproducible Security Research Plan

2026-10-13. **All E01–E17 below are experiment designs: NOT EXECUTED in this research package.** Historical results in [B](B-technical-gap-analysis.md) justify reuse but do not satisfy these new acceptance records. IDs here are local research-plan IDs, not additions to canonical CC-* tests.

## Common disposable protocol

Use the current pinned PostgreSQL 16.4 image/digest and existing native demo in B. Synthetic ordinary heap tables only: `repair_items(id, tenant_id, status, revision)`, a second independently budgeted table, and a sibling audit table. First milestone should reuse existing demo names/layout where possible; this notation is conceptual, not an implementation directive. Fixture admin installs the module and grants; writer cannot own tables, set bypass privileges or read admin credentials. Observer uses a **new trusted connection** after writer transaction termination.

Reset fixtures between scenarios. Freeze repository SHA, image digest, exact version, isolation, grants, trigger/catalog fingerprints, initial rows, expected final rows and expected event sequence. No production dumps, real users, network side effects, paid service or model subscription is necessary. Disable outbound effects in any replay fixture. Do not invoke a production endpoint to learn whether it is production.

For durable-state oracle, compare exact ordered rows and sibling audit rows, not just command tags or logs. For repeated/no-op events, final state is insufficient: the known synthetic command sequence and an independent fixture-only event trace must establish event count. Any extra audit trigger changes the trigger graph and must be evaluated as a separate fixture; do not silently insert it into the currently supported generic-table installation. Crash/acknowledgment tests also query committed operation markers and the proposed ledger from a new connection. An unavailable oracle yields **UNKNOWN**, never success.

Proposed evidence fields: schema version; source SHA; scenario; declared boundary; expected classification; observed client outcome; SQLSTATE; initial/final oracle hashes plus synthetic row artifact; event metric; policy/grant fingerprints; server/image; timestamps; cleanup result. Avoid secret-bearing connection strings and real row data. A checksum identifies an artifact; it does not authenticate an untrusted producer.

Classifications must separate `EXPECTED_ALLOW`, `EXPECTED_DENY`, `EXPECTED_COUNTEREXAMPLE`, `UNSUPPORTED`, `UNKNOWN`, and `REGRESSION`. A split-transaction counterexample is success for documenting a transaction-only boundary, but failure for a claimed task-wide boundary.

## Adversarial interpretation and stopping

Stop the relevant branch on any durable excess under its declared boundary. Preserve the counterexample, source SHA and fixture. Do not weaken oracle assertions, switch metrics from events to distinct IDs, exclude a failing supported path after the fact, or promote an UNKNOWN to PASS.

An unchanged restricted procedure satisfying E10–E13 is useful counterevidence to a native product, even if it supports less flexible SQL. Successful idempotency/origin-filter controls can invalidate F13/F17 as differentiated products. A clean branch-only workflow can make inline production enforcement unnecessary. Unknown provider installation or unpredictable overhead can prevent productization despite correct local semantics.

Independent replication means another developer can run from a clean checkout with recorded prerequisites and no author-specific state. No merchant interviews are required for this gate. Later adoption evidence must be collected separately; publishing test output does not establish willingness to pay.
