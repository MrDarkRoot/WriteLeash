# CommitCap Free V0.1 — database operator setup

CommitCap protects one certified operation: the Redirection 5.5.2 global/select-all Bulk Disable. The protected runtime needs a **trusted, one-time database setup** before the WordPress Admin can enable the certified operation. This document is for the database operator who performs that setup. A normal site administrator never needs to run SQL and never enters database credentials in WordPress.

## Who does what

| Role | Responsibility |
| --- | --- |
| Database operator (DBA, host, DevOps) | Runs the reviewed provisioning plan once, adds the runtime constants to `wp-config.php`, and later rotates or removes the setup if needed. |
| Site administrator | Uses Tools → CommitCap to confirm readiness, set the logical budget, enable or disable the certified operation, and read the local outcome. No SQL, no PHP. |

## Prerequisites

* WordPress with CommitCap installed and active, and Redirection **5.5.2** installed and active.
* A pinned, supported engine: **MySQL 8.0.44** or **MariaDB 10.11.15** (the release-matrix-tested builds). Other builds are not certified in V0.1.
* A trusted database connection (temporary installer/administrator account or root) with the privileges to create a user, grant and revoke, create routines and triggers, and alter the runtime account. For routine/trigger definition inspection, MySQL 8.0 additionally needs `SHOW_ROUTINE`; MariaDB needs `SELECT` on the `mysql` schema.
* For credential rotation with drain, the operator connection also needs global `PROCESS` visibility and other-user `KILL` authority (`CONNECTION_ADMIN` or `SUPER`).

The installer/root credential is used only for this one-time setup and is never stored in WordPress, never saved in `wp_options`, and never required by normal plugin requests.

## Reviewed provisioning plan

CommitCap deliberately exposes no web or Admin provisioning form. All setup statements are generated by the reviewed `CommitCap\Provisioning_Plan` service, rendered as inspectable SQL, and applied once by the operator. The plan never drops application tables or their rows, and it refuses to replace any unrecognized database object.

### 1. Generate and review the plan

Save this as a temporary, trusted script (run it with WP-CLI; do not leave it in the web root) and review the rendered SQL before applying anything:

```php
<?php
// Trusted one-time provisioning. Run with: wp eval-file provision-commitcap.php
$schema = DB_NAME;
$user   = 'commitcap_runtime';   // choose a clear, site-specific name
$host   = 'localhost';           // account host restriction, see step 3
$secret = getenv( 'COMMITCAP_RUNTIME_SECRET' );

if ( ! is_string( $secret ) || '' === $secret ) {
	fwrite( STDERR, "Set COMMITCAP_RUNTIME_SECRET first.\n" );
	exit( 1 );
}

$plan = \CommitCap\Provisioning_Plan::install(
	$schema,
	$user,
	$host,
	$secret,
	array( $GLOBALS['wpdb']->prefix . 'redirection_items' => 2000 )
);

echo $plan->render_sql( true ); // Redacted review copy. Never echo the raw secret.
```

The plan creates: one restricted runtime account; the `commitcap_v01_state` helper table; five reviewed `SQL SECURITY DEFINER` routines (`commitcap_v01_open`, `commitcap_v01_close`, `commitcap_v01_count`, `commitcap_v01_policy`, `commitcap_v01_attest`); `EXECUTE` on exactly those five routines; read-only `SELECT` on the helper table; and `SELECT, UPDATE` plus one identity-scoped `BEFORE UPDATE` policy trigger on the certified target table with physical ceiling 2000.

### 2. Apply the plan with the trusted installer connection

```php
$installer = new wpdb( $installer_user, $installer_password, DB_NAME, $installer_host );
$installer->suppress_errors( true );
$result = $plan->apply( $installer );
var_export( $result ); // success, state and step details; secrets are never echoed
```

Apply preflight refuses to overwrite a foreign helper shape, a foreign routine body, a foreign trigger that reuses a CommitCap name, or a pre-existing account with grants outside the reviewed surface. If the run is interrupted, replay the same plan: the steps are deterministic and safe to repeat.

### 3. Add the runtime constants to wp-config.php

```php
define( 'COMMITCAP_DB_USER', 'commitcap_runtime' );
define( 'COMMITCAP_DB_PASSWORD', 'REPLACE_WITH_THE_GENERATED_SECRET' );
define( 'COMMITCAP_DB_HOST', 'localhost' );
define( 'COMMITCAP_DB_NAME', 'REPLACE_WITH_YOUR_DATABASE_NAME' );
```

`COMMITCAP_DB_HOST` is the **account host restriction** used when the plan creates the database user; it is not a connect host. CommitCap connects the restricted account the same way normal WordPress connects (the normal database host from your configuration), which is what keeps the runtime account reachable on typical hosts. Choose the account host to match how your WordPress connects, commonly `localhost`; a host such as `%` widens where the credential may be used.

Only the operator adds these constants. The Admin never sees or stores database credentials.

### 4. Verify and enable

Open **Tools → CommitCap**. The readiness line should report **READY**, with the Doctor showing PASS and the restricted runtime available. If it does not, see the reason shown on the page before enabling anything. Then choose the logical budget L (0–2000), save it, and enable the certified operation. Normal use then happens in Redirection: Redirects → select all matching → Bulk Actions → Disable.

### 5. Optional: provision the disposable demo

The disposable demo runs on CommitCap-owned synthetic data only. To enable it, provision the demo target with the same reviewed services from a trusted script (uses the same installer connection):

```php
$setup = new \CommitCap\Disposable_Demo_Setup( $installer, $user, $host );
$setup->setup();
$setup->reset(); // one deterministic seed; normal demo runs never reset.
```

Without this optional step, the production certified operation can still be READY.

## Exact runtime privilege surface

The restricted account holds, in total:

* `EXECUTE` on exactly the five reviewed routines.
* `SELECT` on the helper table `commitcap_v01_state`.
* `SELECT, UPDATE` on the certified target table only.

The runtime account has no `INSERT`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `TRIGGER`, `GRANT` or `REVOKE` authority. It cannot read WordPress options or any other application table. Normal WordPress keeps its ordinary database account; CommitCap does not restrict the site-wide WordPress database identity and does not claim to.

## Credential rotation

Rotation is a two-part operator action, not a password edit alone:

1. Apply the reviewed rotation plan (`Provisioning_Plan::rotate_credential`) with a new secret; it records a durable safety marker before `ALTER USER`.
2. Drain surviving sessions: on both pinned engines, `ALTER USER` does not terminate already-authenticated connections. The plan terminates the runtime account's remaining sessions, verifies zero remain, and only then clears the marker. If the drain cannot be proven, Doctor keeps the operation not-ready and the Admin refuses to enable protected work until a successful standalone drain (`Provisioning_Plan::drain`) completes.

Update `COMMITCAP_DB_PASSWORD` in `wp-config.php` to the new secret as part of the rotation.

## Removal and uninstall

* Removing the protection only: apply `Provisioning_Plan::remove_target` — the policy trigger and target grants are removed, the application table and all rows stay.
* Full operator cleanup: apply `Provisioning_Plan::uninstall` — CommitCap triggers, the five routines, the helper table and the runtime account are removed. Application tables and Redirection data are never touched.
* WordPress uninstall (deleting the plugin from the Plugins screen) removes only CommitCap's local WordPress state. It never removes database users, grants, routines, triggers or Redirection data, and it needs no installer credential. It is the operator's job to remove the database runtime when it is no longer wanted.
